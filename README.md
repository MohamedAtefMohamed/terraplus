# TerraPulse

**Understand Earth's changes. Before they become disasters.**

TerraPulse is an Earth Surface Intelligence Platform built for the **NASA Space Apps Challenge**. It turns synthetic-aperture-radar (SAR) observations into an interactive change-analysis workflow: discover an area, inspect acquisition metadata, compare two scenes, visualise a change layer, follow a timeline, and read a careful explanation that separates observation from interpretation.

> **Demonstration data notice**
> The bundled observations are a **deterministic synthetic SAR dataset** generated by TerraPulse. The coordinates and demonstration footprints are real; the radar backscatter pixels are **not**. No bundled pixel is a NISAR, Sentinel-1 or other real satellite acquisition. TerraPulse never presents synthetic data as NASA data and is not an operational, emergency or safety product.

## What is implemented

### P0 — complete

- Polished landing page with product identity, mission context, scenario cards and demo-data disclosure.
- Intelligence dashboard with aggregated statistics, recent analyses, observation records, environmental indicators, NISAR integration status and mode disclosure.
- Fully interactive MapLibre map with pan/zoom, monitored-area selection, observation markers, date filtering, footprint layers, change/water overlays, basemap switching (including an offline solid fallback), legend and selected-area panel.
- Live NISAR metadata footprints drawn on the map from real ASF granule geometry, with browse thumbnails, click-to-select linking and explicit “metadata only / not processed” labelling.
- Real paired-raster comparison pipeline implemented in Python with Rasterio, NumPy, SciPy, Shapely and Pillow.
- Before/after draggable comparison, change statistics, quality indicators, method details and limitations.
- Temporal analysis page with observation timeline, metrically derived trend charts, consecutive-pair change chart, availability table and per-observation details.
- AI insights page with a fully functional **deterministic explanation engine** (no API key needed) and an optional opt-in LLM narration path.
- Methodology and data-policy page suitable for non-technical judges.
- Three seeded demonstration areas, four acquisition dates each, and nine persisted analyses.
- Clear DEMO / SAMPLE / LIVE data-mode status throughout the interface.
- Live NISAR granule **metadata discovery** through the ASF DAAC with a generic STAC fallback adapter.
- SQLite persistence, demo seeding, provenance records, API docs, CORS, structured logging, input validation, request-size limit and compare rate limiting.
- Dockerfiles, Docker Compose, native development scripts, env examples and tests.

### Explicitly not implemented

- Authenticated NISAR product download.
- Mission-specific calibration, terrain correction and InSAR displacement processing.
- Ground-truth validation of change signals.
- Operational flood mapping or emergency alerting.

These are stated in the UI and API rather than simulated.

## Architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Next.js frontend (3000)                     │
│  app/ routes · React 19 · TanStack Query · Zustand-ready            │
│  MapLibre GL · Recharts · Tailwind v4 · Radix UI · Framer Motion    │
└───────────────┬─────────────────────────────────────────────────────┘
                │  JSON + PNG / GeoJSON over HTTP
┌───────────────▼─────────────────────────────────────────────────────┐
│                        FastAPI backend (8000)                       │
│  api/routes · Pydantic schemas · rate limit · request logging       │
│                                                                     │
│  services/             services/nasa/          services/processing/ │
│  analysis_service      asf_client              raster_loader        │
│  timeline_service      catalog_client          preprocessing        │
│  dashboard_service     nisar_client             normalization       │
│  explanation_service   data_normalizer         change_detection     │
│  mode_service          sample_loader           water_change         │
│                                                statistics           │
│                                                quality_assessment   │
│                                                visualization        │
│                                                geojson + pipeline   │
└──────────┬──────────────────────────┬───────────────────────────────┘
           │                          │
     SQLite metadata            Disk raster assets
     locations, observations,   demo GeoTIFFs, PNG previews,
     products, analyses,        change overlays, GeoJSON
     statistics, provenance     (never stored inside SQLite)
```

**Data flow**

1. On first startup, the backend creates the SQLite schema and generates the pseudo-random demo GeoTIFFs (deterministic seeds).
2. Observations and precomputed analyses are stored in SQLite; large rasters and derived assets stay on disk.
3. The frontend fetches only JSON; map overlays and previews are loaded from `/media`.
4. A user-running comparison calls `POST /api/analysis/compare`, which loads both rasters, validates alignment, computes the change products, persists the analysis and returns its statistics and asset URLs.
5. Explanations are generated on demand from persisted facts; the LLM path is optional.

## Configuration

Configuration is environment-driven. The backend reads the process environment and optional `.env` files (`backend/.env` or the repository-root `.env`). The frontend reads `NEXT_PUBLIC_API_URL` **at build time**, so rebuild the frontend if that value changes.

| Variable | Default | Purpose |
|---|---|---|
| `DATA_MODE` | `demo` | `demo`, `sample`, `live` or `auto` |
| `LIVE_DISCOVERY_ENABLED` | `true` | Enables ASF/STAC metadata search |
| `NASA_EARTHDATA_USERNAME` | empty | Optional; not required for metadata discovery |
| `NASA_EARTHDATA_PASSWORD` | empty | Optional; required for future authenticated download |
| `ENABLE_LLM_NARRATION` | `false` | Opt-in flag for optional LLM narration |
| `OPENAI_API_KEY` | empty | Required only when narration is enabled |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | OpenAI-compatible endpoint |
| `OPENAI_MODEL` | `gpt-4o-mini` | Narration model |
| `CORS_ORIGINS` | `http://localhost:3000,http://127.0.0.1:3000` | Comma-separated allowed origins |
| `DATA_DIR` | `backend/data` | Raster, media and SQLite location |
| `DATABASE_URL` | SQLite under `DATA_DIR` | Override for another SQL database |
| `MAX_ANALYSIS_PIXELS` | `4000000` | Rasters above this are downsampled in memory |
| `COMPARE_RATE_LIMIT_PER_MINUTE` | `40` | In-memory compare-endpoint rate limit |
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` | Backend URL visible to the browser. For native frontend runs, put this in `frontend/.env.local` (the root `.env` is read by the backend, not Next.js). |

### Optional LLM narration

The deterministic explanation engine is the default and requires no key. Narration is deliberately opt-in, so an ambient `OPENAI_API_KEY` on the host cannot silently trigger paid calls:

```bash
ENABLE_LLM_NARRATION=true
OPENAI_API_KEY=...
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_MODEL=gpt-4o-mini
```

If the provider fails, the app returns the deterministic explanation with a visible note. Statistics, quality values and limitations are never generated by the LLM.

## NASA NISAR integration

### Implemented

- Modular adapters:
  - `backend/app/services/nasa/asf_client.py` — ASF DAAC granule search (`platform=NISAR`).
  - `backend/app/services/nasa/catalog_client.py` — generic STAC search with CMR/ASF STAC endpoint.
  - `backend/app/services/nasa/nisar_client.py` — mission facts, product-family catalog, discovery facade, analysis-method guardrails.
  - `backend/app/services/nasa/data_normalizer.py` — normalises ASF/STAC records.
  - `backend/app/services/nasa/sample_loader.py` — manifest-driven SAMPLE adapter.
- Search by bounding box and date range, metadata normalisation, provenance and access notes.
- Live results are rendered as real granule footprint polygons on the map (toggleable), with ASF browse thumbnails and result-card ↔ footprint selection. These are explicitly **not** analysis layers.
- Frontend **Map → NISAR live** panel with bbox/date search and real granule result cards.
- Product-family metadata (RSLC, GSLC, GCOV, GUNW, GOFF) with explicit “supported in MVP: false” markers.
- A guardrail that forbids displacement analysis on unsuitable products.

### Live discovery status

Live NISAR metadata search was executed against ASF during development and returned real provisional NISAR granule metadata (e.g. `NISAR_L2_PR_GCOV_...` items with acquisition times, orbit path/frame, browse links and product URLs). This is **metadata only**.

### Not implemented

- Authenticated product download (NASA Earthdata Login required).
- HDF5/GCOV ingestion, calibration, terrain correction and InSAR displacement.
- Any presentation of discovered granules as processed analysis data.

### Enabling future live processing

1. Add Earthdata-authenticated download with a secure token/session mechanism on the backend.
2. Register a product-family adapter that understands the actual HDF5/GeoTIFF layout and calibration metadata.
3. Replace the demo observation provider with the adapter output while keeping the change-detection interface.
4. Rework thresholds only after validation against a known reference dataset.

The SAMPLE path allows a team to stage real, properly attributed data quickly without redesigning the application. See `backend/data/sample/manifest.json` schema in `sample_loader.py`.

## Data modes and attribution policy

| Mode | What it means | Current status |
|---|---|---|
| **DEMO** | Synthetic scenes generated by TerraPulse. Real coordinates, fabricated radar backscatter. | Active and fully functional |
| **SAMPLE** | Real sample products staged by the operator, described by a manifest with original attribution. | Adapter present; no sample data bundled |
| **LIVE** | Real NISAR granule metadata discovered through ASF. | Discovery enabled; download/processing not implemented |

- The active mode and analysis mode are always surfaced in the header and pages.
- If `DATA_MODE=sample` is requested without a staged manifest, the app falls back to DEMO and shows the fallback reason.
- If `DATA_MODE=sample` is selected with a staged manifest, discovery can report SAMPLE while the label becomes “SAMPLE STAGED · DEMO ANALYSIS”: no sample-raster analysis pipeline is wired into this MVP, so every displayed comparison remains the DEMO dataset.
- If `DATA_MODE=live` is selected, the label becomes “LIVE DISCOVERY · DEMO ANALYSIS”, because raster analysis still uses DEMO data.
- The demo GeoTIFF tags contain `IS_SYNTHETIC=true`, the mission name `TerraPulse Synthetic Demo` and a disclaimer. The database also records `is_synthetic` and provenance for every observation and analysis.

## Demonstration scenarios

All three areas use real bounding boxes; every radar pixel is synthetic. Four dates per area, nine persisted analyses.

| Area | Coordinates (center) | Focus | Demo dates |
|---|---|---|---|
| Sundarbans Delta, Bangladesh/India | 21.93°N, 89.19°E | Monsoon water expansion | 2025-05-18, 2025-06-27, 2025-08-14, 2025-10-03 |
| Atchafalaya Basin, USA | 29.67°N, 91.38°W | Coastal wetland water variability | 2025-03-12, 2025-06-05, 2025-09-09, 2025-11-01 |
| Mekong Delta, Vietnam | 10.09°N, 106.05°E | Seasonal delta inundation | 2025-04-08, 2025-07-19, 2025-09-23, 2025-11-12 |

The generator creates coherent water bodies from a fixed multi-scale field plus a river/coast mask, then applies a target water fraction per date. Land is assigned plausible dB classes (water, vegetation, bare, urban) and four-look multiplicative speckle. Nodata is injected deliberately to exercise quality handling. The scenes are generated at 256×256 in EPSG:4326 and stored as float32 GeoTIFFs with `-9999` nodata.

> The water-fraction trajectory is illustrative. It is not a record of any real flood event.

## Change-detection method

### Pipeline

1. **Load and validate** both single-band rasters; reject missing files, unsupported formats, implausible values and <5% valid pixels.
2. **Check alignment**: identical shape, CRS and geotransform, otherwise reject the comparison.
3. **Prepare**: replace nodata with the scene median, apply a 5×5 median filter as a transparent speckle-reduction screen, re-apply the valid mask.
4. **Difference**: `ΔdB = later_dB − earlier_dB` (equivalent to `10·log10(P_later / P_earlier)` for calibrated power).
5. **Classify**: `increase = ΔdB > +threshold`, `decrease = ΔdB < −threshold`, using a default ±3.0 dB configurable threshold.
6. **Water indicator**: `water = dB < water_threshold` (default −17.0 dB); derive `new_water = after & !before` and `lost_water = before & !after`.
7. **Statistics**: pixel counts, area from the affine pixel size at the area's latitude, fractions, means/median change, alignment and robustness metrics.
8. **Quality**: composite score from valid coverage, robust MAD-based residual noise and grid alignment. It describes the comparison, not event probability.
9. **Render**: PNG change/water overlays and simplified GeoJSON polygons, with metadata and disclaimers.

### Equations

```
ΔdB            = 10 · log10(P_later / P_earlier)
changed        = |ΔdB| > change_threshold
new_water      = (later_dB < water_threshold) ∧ ¬(earlier_dB < water_threshold)
lost_water     = (earlier_dB < water_threshold) ∧ ¬(later_dB < water_threshold)
pixel_area_km² = |Δlon|·111.320·cos(lat) · |Δlat|·110.574
```

### Why these thresholds?

They are **configurable screening defaults chosen for the demonstration**, not universal scientific constants. Real work requires mission-specific calibration, incidence-angle handling, polarimetric context, seasonality and ground validation.

### Confidence semantics

The confidence score combines coverage (50%), residual noise (30%) and alignment (20%). It is explicitly labelled as **processing quality**. It is not the probability that a flood or any other event occurred.

## Scientific limitations

Read these as part of the product, not as fine print.

1. **No cause attribution.** A radar backscatter change does not identify flooding, damage, vegetation loss or any specific process.
2. **Confounding surface properties.** Roughness, vegetation structure, soil moisture, tillage, snow, radar shadow and acquisition geometry can all change dB.
3. **Single-polarisation VV.** No cross-polarisation or polarimetric decomposition is used.
4. **No incidence-angle normalisation.** Comparison assumes reasonably compatible acquisition geometry.
5. **Speckle screening only.** A 5×5 median filter is transparent and cheap, not a validated production speckle workflow.
6. **Configurable thresholds.** ±3.0 dB and −17.0 dB are demo defaults, not universal truth.
7. **No validation data.** No optical imagery, gauge records or field reports are used to validate a change.
8. **Quality ≠ event probability.** The confidence score describes processing quality only.
9. **Synthetic demo.** Coordinates are real, pixels are fabricated. The timeline is illustrative.
10. **Live products are not processed.** ASF results are metadata; authenticated download, calibration and InSAR are future work.
11. **Not operational.** Not for emergency response, safety decisions, insurance, damage assessment or regulatory use.

### PostgreSQL/PostGIS migration

The schema intentionally uses portable SQLAlchemy types and stores geometry as GeoJSON-compatible JSON. To migrate:

1. Set `DATABASE_URL=postgresql+psycopg://...`.
2. Run the same SQLAlchemy metadata against PostgreSQL.
3. Optionally add PostGIS `Geometry` columns and spatial indexes for production-scale queries.
4. Rasters remain on object storage (S3/GCS) with signed access; the database stores pointers and provenance.

## Troubleshooting

**The frontend shows “Cannot reach the TerraPulse API”.**
Start the backend on port 8000 and confirm `curl http://localhost:8000/api/health`. If the API is elsewhere, rebuild the frontend with the correct `NEXT_PUBLIC_API_URL`.

**Port already in use.**
Stop the existing service or change ports. CORS and `NEXT_PUBLIC_API_URL` must match the chosen ports.

**Map tiles do not load.**
The analysis overlays still work. Use **Map → Layers → Solid fallback**. Basemap tiles require outbound access to Esri/CARTO.

**Map shows “Initialising map surface”.**
WebGL is required for MapLibre. Enable hardware acceleration or try a current Chrome/Firefox/Safari. In headless Chrome, pass `--enable-unsafe-swiftshader`.

**MapLibre worker error in a custom deployment.**
`public/maplibre-gl-worker.mjs` is copied from the installed MapLibre version and set via `maplibregl.setWorkerUrl(...)`. Keep that file in sync when upgrading `maplibre-gl`.

**Demo data is stale or corrupted.**
Run `make reset-demo` and restart the backend.

**Live NISAR search returns no results or an error.**
Absence of results does not mean the mission has no data; adjust dates/bbox or check outbound network access. The application remains fully functional in DEMO.

**Rasterio install fails natively.**
Use Python 3.12–3.14 with a platform compatible with manylinux wheels, or use Docker. On Debian/Ubuntu, `libgomp1` is the only extra runtime dependency used by the container.
